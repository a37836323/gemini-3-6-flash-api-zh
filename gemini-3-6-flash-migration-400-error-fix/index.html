换成 gemini-3.6-flash 后报 400：迁移清单逐项怎么改

把模型从 gemini-3-flash-preview、gemini-3.5-flash 换成 gemini-3.6-flash 之后请求返回 HTTP 400，先检查请求里有没有预填的 model 回合，以及是否同时写了 thinking_level 和 thinking_budget。Google 官方「What's new in Gemini 3.6 Flash and 3.5 Flash-Lite」页写明，从这两个模型起，最后一个非空回合是 model 回合的请求会直接返回 HTTP 400；temperature、top_p、top_k 现在会被忽略，之后的新版本会以 400 拒绝。迁移清单还要求删掉 candidate_count、把 thinking_budget 换成 thinking_level，并检查函数调用写法。下面按官方文档逐项说明怎么改、改完怎么验证。

哪些代码会碰到这些变化

Google 模型弃用页（https://ai.google.dev/gemini-api/docs/deprecations）把 gemini-3.6-flash 列为 gemini-3-flash-preview、gemini-2.0-flash 等模型的推荐替代。gemini-3.5-flash 一行写明：该端点不会关闭，API 请求会自动转到 gemini-3.6-flash，并且在 Google AI Studio 里已经不能选择。

也就是说，直接调用 Google 官方 API 时，即使代码里写的还是 gemini-3.5-flash，请求也会由 gemini-3.6-flash 处理，本页列出的规则同样适用。

gemini-3.6-flash 的模型页写明它是稳定版，属于上一代 Flash 模型，仍可用于生产；最新的 Flash 模型是 Gemini 3.8 Flash。弃用页对 gemini-3.6-flash 写的是尚未公布下线日期。官方迁移指南列出的迁移来源是 Gemini 3.5 Flash、Gemini 3 Flash（Preview）和 Gemini 3.1 Pro。

官方把这次的接口变更说明为适用于 3.6 Flash、3.5 Flash-Lite 以及之后所有版本，所以以后再换到更新的模型，这些改动同样需要保留。

预填 model 回合：直接返回 400

官方原文的意思是：如果请求里最后一个非空回合是 model 回合，请求会失败并返回 HTTP 400。所谓预填充，是在 contents 末尾放一段角色为 model 的文字，例如先写好 JSON 的开头，让模型接着往下写。

这条规则针对的是最后一个非空回合。多轮对话历史里 user 和 model 正常交替出现不受影响，只要最后一个非空回合不是 model。

官方给出的替代做法有两种：把格式和口吻要求写进 system_instruction；或者用结构化输出（Structured outputs，https://ai.google.dev/gemini-api/docs/structured-output）约束返回格式。原来用预填充来固定输出 JSON 格式的，可以改用结构化输出。

排查时把最终发出去的请求体打印出来，确认 contents 的最后一个非空回合不是 model。用了封装库的，以实际发出的请求体为准。

temperature、top_p、top_k 和 candidate_count

官方迁移指南写明：temperature、top_p、top_k 这三个采样参数已弃用，现在会被忽略；之后的新版本会以 HTTP 400 拒绝它们，所以应当删掉。在 3.6 Flash 上带着它们不会直接报错，但设置也不会生效。

影响在于，原来靠把 temperature 调到 0 来获得较稳定输出的代码，在 3.6 Flash 上这个设置不再起作用。官方建议：需要更确定的输出时，在系统指令里写出明确的规则。

迁移清单同时要求删掉 candidate_count，原话是 Gemini 3 及之后的模型不支持这个参数。

补充一点：已标注「将被移除」的 Gemini 3 开发者指南（https://ai.google.dev/gemini-api/docs/gemini-3）曾建议 temperature 保持默认 1.0，并说低于 1.0 可能导致循环或效果变差。3.6 Flash 的迁移指南是更新的说法，直接删除这些参数即可。

thinking_budget 换成 thinking_level

迁移清单要求把 thinking_budget 换成 thinking_level，清单里给的取值是 medium 或 high。官方 Thinking 页的表格写明：gemini-3.6-flash 默认开启思考，默认档位是 medium，可选 minimal、low、medium、high；表中没有关闭思考的选项，最低一档是 minimal。

从 gemini-3-flash-preview 迁移时要留意默认值：同一张表里 gemini-3-flash-preview 的默认档位是 high，而 gemini-3.6-flash 是 medium。如果原来的代码没有写思考等级、依赖默认值，换模型后实际档位会从 high 变成 medium；想保持原来的档位，就显式写 high。从 gemini-3.5-flash 迁移则不受影响，官方写明 3.6 Flash 的默认值与 3.5 Flash 相同，都是 medium。

已标注将被移除的 Gemini 3 开发者指南写明：thinking_budget 为向后兼容仍被接受，但同一个请求里同时写 thinking_level 和 thinking_budget 会返回 400 错误。所以改的时候要删掉旧字段，不要在旧字段旁边再加一个新字段。

官方示例用的是 Interactions API，思考等级写在 generation_config 下的 thinking_level。用 generateContent 接口时，思考设置写在 generationConfig 的思考配置里，具体字段名请以 API 参考页（https://ai.google.dev/api/generate-content）的 GenerationConfig 一节为准。

函数调用和思维签名要检查什么

迁移清单要求审查函数调用写法。第一条是把多模态素材放进函数返回内容里：Function calling 页说明，Gemini 3 系列可以在 function_result 的 result 中放一个或多个内容块，每个内容块都要写明 type，例如 text 或 image。

第二条是用两个换行符（\n\n）分隔内联指令，官方清单没有进一步展开。

第三条是 Malformed_Function_Call。Function calling 页写明：如果提示词要求模型在调用工具前先输出 XML、YAML、JSON 之类的结构化文字（例如一个 UPDATE 块），工具调用偶尔会以 Malformed_Function_Call 失败。官方首选做法是让模型把调用前的说明写进一个专门的 update 函数调用，声明 previous_step、plan、next_step、external 四个必填字符串参数；其次是让模型改用 Markdown 标题写说明；或者干脆不要求模型在调用工具前输出文字。

思维签名方面，Function calling 页写明 SDK 会自动处理思维签名。自己管理对话历史（无状态方式）时，Thinking 页要求把模型返回的 thought 块原样回传，不能删除或修改，切换模型时也一样；使用有状态方式（store 为 true 并传 previous_interaction_id）时由服务端处理。API 参考里有一个结束原因 MISSING_THOUGHT_SIGNATURE，含义是请求里至少缺了一个思维签名，遇到它就检查历史里的 thought 块是否被丢掉了。

不报错但行为变了的地方

官方迁移指南提到一项行为变化：3.6 Flash 比 3.5 Flash 更常在修改之前先运行诊断脚本。这样准确率更高，但在常规的前端工作上可能多出一些探索步骤。

另一项是界面样式：官方写明 3.6 Flash 生成的代码功能性更好，但人工评审更偏好旧模型的视觉样式，提供明确的设计规范会有帮助。

官方同时写明 3.6 Flash 在多步工作流里需要的推理步骤、轮次和工具调用比 3.5 Flash 少，用量变化请以自己的账单为准，价格以官网价格页为准。

改完怎么验证

第一步，先调用 /v1/models，确认模型列表里有 gemini-3.6-flash，并确认业务代码里的模型名已经改过来。

第二步，发一个最小请求：contents 最后一个非空回合是 user；不带 temperature、top_p、top_k、candidate_count；思考参数只写 thinking_level 一种。确认返回 200 且有文本，原来的 400 不再出现。

第三步，确认思考档位生效。generateContent 的返回里 usageMetadata.thoughtsTokenCount 是思考 token 数。把同一个问题分别用 low 和 high 跑一次，对比这个数，确认设置确实传到了模型。

第四步，原来用预填充控制格式的，改成结构化输出后，用几条真实样本检查返回内容能否按预期解析；原来用函数调用的，跑一轮完整的多轮工具调用，确认没有出现 Malformed_Function_Call 或 MISSING_THOUGHT_SIGNATURE。

通过 OpenLux 中转调用时要注意什么

OpenLux 价格接口里在售的模型 ID 有 gemini-3.6-flash，也有 gemini-3.5-flash、gemini-3-flash-preview 和 gemini-3.8-flash。

弃用页说的 gemini-3.5-flash 自动转到 gemini-3.6-flash，是 Google 官方 API 的行为；通过中转调用 gemini-3.5-flash 时最终由哪个版本处理，本页没有核实。迁移时建议直接把模型名改成 gemini-3.6-flash，再按上面的清单改请求，行为更明确。

用 Gemini 原生格式时，Base URL 填 https://api.openlux.ai，请求路径是 /v1beta/models/gemini-3.6-flash:generateContent；也可以用 OpenAI 兼容格式，Base URL 填 https://api.openlux.ai/v1。官方示例用的 Interactions API（/v1beta/interactions）不在已核实的入口里，不要默认它能用。OpenAI 兼容格式下思考参数经过中转后怎样传给模型没有逐项核实，请按上一节的方法用最小请求和思考 token 数确认。
