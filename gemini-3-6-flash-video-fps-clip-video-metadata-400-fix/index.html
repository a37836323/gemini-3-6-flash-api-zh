gemini-3.6-flash 视频帧率与截取片段的正确写法

用 gemini-3.6-flash 分析视频时，想把抽帧率从默认的每秒 1 帧调高或调低、或者只分析其中一段，写法取决于你用的接口：Interactions 接口（interactions.create、/v1beta/interactions）要把 fps、start_offset、end_offset 写进视频输入块的 processing 对象，并且只在 static 模式下有效；照旧教程传 video_metadata 会被拒绝，返回 400 Unknown parameter。generateContent 接口则在 Part 上用 videoMetadata，起止时间是带 s 的秒数字符串。下面按 Google 官方视频理解指南和 API 参考逐项说明怎么改、改完怎么确认生效。

先确认你用的是哪个接口

Gemini API 有两套调用视频的方式，帧率和截取的写法不一样，混用就会报错或不生效。代码里调用 client.interactions.create，或请求地址是 /v1beta/interactions 的，属于 Interactions 接口；调用 generate_content，或请求地址是 /v1beta/models/gemini-3.6-flash:generateContent 的，属于 generateContent 接口。

Google 官方视频理解指南（https://ai.google.dev/gemini-api/docs/video-understanding，页面标注 2026 年 10 月 13 日更新）的代码示例全部使用 Interactions 接口。generateContent 接口的字段定义在 API 参考页（https://ai.google.dev/api/generate-content）的 Part 和 VideoMetadata 一节。

两种接口都默认按每秒 1 帧静态抽帧（官方称为 static 处理）。官方指南提醒，默认 1 帧每秒可能漏掉快速动作或镜头切换的细节；反过来，对讲座、会议这类画面变化慢的长视频，可以降低帧率来减少帧的 token。

Interactions 接口：fps 和起止时间写进 processing 对象

官方指南写明：可以在 processing 配置对象里传 fps 参数来自定义抽帧率，也可以在同一个对象里写 start_offset 和 end_offset 来截取视频。processing 是 input 数组里视频块（type 为 video）的一个字段，和 uri、mime_type 并列，不是 interactions.create 的顶层参数，也不放在 generation_config 里。

官方示例的写法是：视频块里写 "processing": {"type": "static", "fps": 0.5}，表示每 2 秒抽 1 帧；截取片段写 "processing": {"type": "static", "start_offset": 1200, "end_offset": 1500}。fps 和起止时间可以写在同一个 processing 对象里，type 都要写成 static。

需要注意两点。第一，官方示例里的 start_offset、end_offset 是不带单位的整数，指南没有写明单位；按示例填整数，再用下文的验证方法确认截取的是想要的那一段。第二，指南没有给出 Interactions 接口里 fps 的取值范围；generateContent 的 API 参考写的是大于 0、不超过 24，可以作为参考，但以实际返回为准。

官方的 Python 示例中 input 用的是字典列表，processing 作为视频字典的一个键直接写进去即可；REST 请求把同样的 JSON 放进请求体的 input 数组。

为什么会报 400 Unknown parameter 'video_metadata'

在 googleapis/python-genai 的 issue 2727（https://github.com/googleapis/python-genai/issues/2727）中，提问者照 Gemini cookbook 的写法给 interactions.create 传 video_metadata=types.VideoMetadata(fps=2)，在 google-genai 2.11.0 上先是被 SDK 拦下，报 TypeError: create() got unexpected keyword argument(s): video_metadata；改用 extra_body 传过去后，接口返回 400 Unknown parameter 'video_metadata'，写成 videoMetadata 也一样。

该 issue 下的回复说明：cookbook 示例领先于当时的正式版 SDK，并引用 Interactions 接口概览文档，指出 video_metadata 字段在 Interactions 接口里还不支持。现行的官方视频理解指南给出的写法就是上一节的 processing 对象，所以 Interactions 接口里应当删掉 video_metadata，改写 processing。

同一个 issue 里，提问者还观察到把 fps 直接写在视频块上（与 uri 并列），或写进 generation_config，请求不会报错，但 usage 里的输入 token 数和不写时完全一样，也就是设置没有生效。这类「不报错但没效果」的写法比 400 更难发现，改完一定要按最后一节对比 token。

反过来，如果你用的是 generateContent 接口，却把 processing 对象照搬过去，也不符合 API 参考里 Part 的字段定义。两种接口的字段不要混用。

generateContent 接口：Part 的 videoMetadata 写法

API 参考写明：Part 上有一个可选的 videoMetadata 对象，只在视频通过 inlineData（内联数据）或 fileData（文件地址）传入时设置。它有三个字段：startOffset、endOffset、fps。

startOffset 和 endOffset 是 Duration 格式的字符串，即以秒计、最多 9 位小数、末尾带 s，例如 "3.5s"。截取第 20 分钟到第 25 分钟，写成 "startOffset": "1200s", "endOffset": "1500s"。写成不带 s 的数字，或者照搬 Interactions 示例里的整数写法，都不符合这个格式。

fps 是数字，表示送给模型的帧率；不写时默认 1.0，取值范围是大于 0.0、不超过 24.0。也就是说 0 不是合法值，想降低帧率要写 0.5、0.2 这样的小数，最高写到 24。

REST 请求里一个视频 Part 的结构是：fileData（含 mimeType 和 fileUri）或 inlineData（含 mimeType 和 data），再加上同级的 videoMetadata，例如 "videoMetadata": {"fps": 2, "startOffset": "60s", "endOffset": "120s"}。官方指南建议单个视频时把文字提示放在视频 Part 之后。

fps、分辨率和 token 的关系

官方指南给出的静态处理计费口径是：media_resolution 设为 low 时每帧 66 个 token，否则每帧 258 个 token；音频按每秒 32 个 token 计。默认（低分辨率）下大约每秒视频 100 个 token，高分辨率下大约每秒 300 个 token。

按这个口径，帧的 token 按抽到的帧数计算：把 fps 从 1 调到 0.5，帧数减半，帧这部分 token 也随之减少；调到 2，帧这部分就会增加。音频部分按视频秒数计，不受 fps 影响。截取片段则同时减少帧和音频的时长。

media_resolution 决定每帧最多分配多少 token，和 processing 互相独立，官方写明可以在同一个视频输入上同时设置。generateContent 的 API 参考里，Part 的 mediaResolution 用 level 字段，可选 MEDIA_RESOLUTION_LOW、MEDIA_RESOLUTION_MEDIUM、MEDIA_RESOLUTION_HIGH、MEDIA_RESOLUTION_ULTRA_HIGH。

指南还写明，1M 上下文的模型默认（低分辨率）大约能处理 3 小时视频，高分辨率约 1 小时；提高 fps 也会让同样时长的视频占用更多上下文。gemini-3.6-flash 的上下文长度以官方模型页为准，费用以官网价格页为准。

开了 agentic 模式就不要再写 fps

官方指南写明，Gemini 4 Argon、3.8 Flash、3.6 Flash 和 3.5 Flash Lite 支持智能体式视频理解：在 Interactions 接口的视频块里写 "processing": "agentic"，模型会自己决定看哪些时间段、以什么帧率查看，而不是固定抽帧。默认仍是 static。

指南同时写明，fps、start_offset、end_offset 这些自定义选项只在 static 模式下支持。agentic 模式下再写这些参数会不会报错，官方没有说明，所以要固定帧率或截取片段，就把 type 写成 static；想让模型自己挑片段，就用 agentic，不要两者混写。

同一个请求里可以放多个视频块，分别写 agentic 和 static，官方示例就是一段讲座用 agentic、一段实验视频用 static。

改完怎么确认设置生效

第一步，用一段几分钟的短视频，在同一个提问下分别发两次请求：一次不写 fps，一次把 fps 设为 0.5（Interactions 写在 processing 里，generateContent 写在 videoMetadata 里）。返回 200 且没有 400 Unknown parameter，说明字段位置被接受。

第二步，对比两次的输入 token：Interactions 接口看返回 usage 里的 total_input_tokens，generateContent 看 usageMetadata 里的 promptTokenCount。按上一节的口径，帧率减半后输入 token 应明显下降；如果两次完全相同，就是遇到了 issue 里那种「写了但没生效」的情况，检查字段是不是写错了位置。

第三步，验证截取：选一段开头和结尾内容明显不同的视频，只截取后半段，问模型视频里出现了什么。回答里不应出现截取范围之外的内容，同时输入 token 应比整段视频少。

长视频请求耗时较长时，官方指南提醒：同步、非流式请求在高负载下可能因为后端重试超出连接或鉴权有效期，表现为意外的 401 Unauthorized 或超时；建议改用流式或后台执行（background 设为 true 后轮询结果）。如果长视频一直 401 而短视频正常，先按这个方向排查，而不是先怀疑 Key。

通过 OpenLux 中转调用时要注意什么

OpenLux 价格接口里在售的模型 ID 有 gemini-3.6-flash，支持的接口类型标注为 gemini（Gemini 原生格式）和 openai（OpenAI 兼容格式）。

用 Gemini 原生格式时，Base URL 填 https://api.openlux.ai，请求路径是 /v1beta/models/gemini-3.6-flash:generateContent，Key 放在 x-goog-api-key 请求头或查询参数 key 里。这条路径走的是 generateContent，所以帧率和截取用上文 Part 的 videoMetadata 写法。videoMetadata 是 Gemini 原生字段，OpenAI 兼容格式下怎么传视频不在本页范围内。

Interactions 接口（/v1beta/interactions）和用 Google Files API 上传得到的文件地址，通过中转能否使用，本页没有核实；本页也没有用真实 Key 跑通过视频请求。建议先用一段较短的视频按上一节的方法验证，确认 token 变化符合预期再放到正式业务里。

Key 在 OpenLux 控制台的令牌页创建；价格以官网价格页为准。
